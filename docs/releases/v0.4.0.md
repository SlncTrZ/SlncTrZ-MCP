# SlncTrZ-MCP v0.4.0

Date: 2026-10-08

## User-visible changes

- Choose Full or Gateway-only during the first OAuth consent. Gateway-only exposes downstream providers and auxiliary services without the gateway's coding/context tools.
- New Gateway-only grants use short-lived access tokens and single-use rotating refresh tokens with no fixed or idle expiry. Acknowledged grant state survives gateway restart and client offline periods until revoked.
- Usage charts visualize gateway-observed traffic. Owner connection controls display and enforce the selected permission ceiling.
- Add repository reconnaissance, architecture planning, context slicing, invariant checking and technical-video skills for explicit project discovery or owner installation. The SEA embeds/seeds only code-review and debug-and-test. Owner-edited harness state remains outside release directories.
- Simplify the README and task-oriented documentation; add native OAuth guidance and the portrait introduction.

## Security-relevant changes

- The Gateway-only ceiling is immutable. Neither a refresh nor Owner controls can promote a Gateway-only consent to Full.
- Validate managed install roots before filesystem mutation; reject overlapping or unsafe layouts.
- Native uninstall preserves legacy/non-owned roots and canonicalizes Windows self-removal paths. The follow-up working-tree fix resolves system CMD/PowerShell absolutely and requires bounded helper startup acknowledgement; startup failure preserves managed files, while successful deletion remains deferred until process exit.
- Regression smoke covers quoted paths, Windows shell PATH and cwd inside the install root. Legacy OAuth migration tests use transactional fixtures and a Windows-specific timeout.
- Patch transitive dev dependency source-map-js to 1.2.2 (GHSA-68fv-2mgg-jv7q); runtime dependency behavior is unchanged.
- Add an append-only, fsync-backed lifecycle operation ledger with bounded payload sanitization and process-identity verification. This is a foundation module, not a wired execution controller.
- Updates retain mandatory Ed25519 publisher signature verification before accepting a release manifest.

## Migration / restart / reauthorization

- Stop or quiesce the gateway and take a coherent backup of state and config before upgrading.
- Opening `oauth-grants.sqlite3` migrates schema v1/v2 to v3. Existing grants keep their profiles and finite lifetimes; they are not silently converted to durable Gateway-only grants.
- Complete fresh OAuth consent with Gateway-only selected to adopt durable onboarding. Full grants retain their existing lifetime policy.
- For installations predating v0.3.6, the inherited migration applies: `audit.sqlite3` receives an additive migration for bounded auth reason/operation fields.
- Restart the installed gateway after update and refresh tool discovery where necessary. In-memory contexts, Owner sessions, pending OAuth transactions and managed tasks must be recreated.

## Supported / prebuilt targets

- Linux x64 and Windows x64 standalone User Install are the release targets, subject to exact-candidate native build and public clean-install acceptance.
- Windows System Install is unsupported. Linux System Install requires separate evidence on a disposable systemd host.
- Source development supports Node `>=22.13.0 <25`; installed SEA binaries include their runtime.

## Known limitations

- The lifecycle ledger is not wired into the gateway or external execution controllers. Task Runner/Coordinator state remains in-memory and does not survive restart.
- Durable Gateway-only authorization does not guarantee uninterrupted network/provider availability; refresh tokens remain single-use and revocation still terminates access.
- Usage is an estimate of gateway-observed data, not provider billing or platform allowance.
- Windows Authenticode signing is not claimed; manifest publisher signature verification remains mandatory.
- This source preparation does not establish that v0.4.0 has been published or promoted. Check the published release status and its acceptance results.

## Rollback

- Use verified immutable release metadata for the previous release.
- A binary that only supports OAuth schema v1/v2 rejects schema v3. Rolling back to v0.3.7 or another pre-v3 binary therefore requires restoring the coherent pre-migration state/config backup while the gateway is stopped; binary-only rollback is insufficient.
- Restoring a backup loses OAuth changes made after that backup. Reconcile/re-authorize affected connections after verifying the restored installation.
- Do not silently downgrade the live database schema. Normal uninstall preserves state/config; that preservation alone does not make an older binary schema-compatible.
