# SlncTrZ-MCP v0.3.5

Date: 2026-09-22

Audit hardening update: 2026-09-25

## User-visible changes

- Adds Owner-only Debate deletion on the `/debate` page. Finished, timed-out (`paused_timeout`), stopped, or still-waiting debates show a Delete control next to Stop; deletion asks for confirmation and removes the debate with its full transcript, then returns to the conversation list.
- Active debates cannot be deleted directly: the Delete control stays hidden until the debate is stopped, so a live turn is never removed from under a participating model.
- Reworks the Owner Console Connections card around the display label: a Full/Gateway-only badge next to the name, no raw grant/client identifiers in the row, and inline rename through a pencil control (Enter applies, Escape cancels).
- Makes all five management cards collapsible with a smooth expand/collapse animation: Connections, Paths, MCP Servers, Commands, and Advanced. The animation is disabled under `prefers-reduced-motion`.
- `/usage` now surfaces bounded degraded/drop health when passive telemetry loses events, without changing MCP results.
- Release bundles now include `manifest.json.sig` for Ed25519 publisher authentication after the signing-enabled trust bootstrap.

## Behavior

- Debate deletion is a hard delete of the debate row; participants and messages follow through existing cascade rules. Deleting an unknown debate returns not-found; deleting an active debate returns a conflict directing the Owner to stop it first.
- A model waiting on a deleted debate observes a clean `debate_not_found` on its next read instead of hanging.
- The Debate MCP surface stays at exactly six tools; deletion exists only on the Owner web path, so model contracts are unchanged.
- Connection rename and per-grant profile switching remain available in the Owner Console. The row-level Client Default action is intentionally removed from the normal UI; the existing Owner CLI/control-plane `client-default` compatibility primitive remains supported for setting the profile of future grants from a client and does not mutate existing grant profiles.
- Successful Owner Console logins do not consume the failed-authentication budget; ten failed passphrase attempts from one direct peer remain bounded, and an exhausted peer budget fails closed with 429 until the window resets.
- Provider stale-session recovery remains no-replay and now has a rolling cross-incident budget so recurrent flapping quarantines instead of recovering forever.

## Security-relevant changes

- `DELETE /owner/api/debates/:id` requires an authenticated Owner session plus CSRF, consistent with the existing stop/resume endpoints.
- Connection listings still expose no bearer/refresh token values or hashes.
- The standalone updater/setup path now requires an Ed25519 publisher signature on the exact canonical `manifest.json` bytes before parsing the manifest or activating a downloaded artifact. The release still verifies declared artifact size and SHA-256 after manifest authentication.
- Signing private material remains CI-only; the standalone runtime embeds only the public verification key. The signing job is tag-only, checks that the tag commit is on `main` history, and references the protected `release-signing` GitHub Environment. External release acceptance must verify Environment reviewer/tag/bypass protections and that the private key has no repository-level duplicate.
- OAuth browser retry, token-exchange diagnostics, failure-safe code redemption and durable-before-visible DCR close the audited failure paths without weakening PKCE, exact redirect/resource binding, or exact Owner Passphrase verification.
- Ingress abort/cancellation classification and metadata-only Runner terminal audit improve forensic evidence without adding request bodies, task text, stdout/stderr, tokens, codes, or credentials to audit.
- Host and Origin validation now precede Owner Console, OAuth, and MCP application dispatch, so the configured public Origin allowlist is enforced consistently on administrative and authorization routes.

## Migration / restart / reauthorization

- Existing v0.3.4 managed state remains valid. `audit.sqlite3` receives an additive migration for privacy-reviewed `auth_reason` / `auth_operation` fields; no destructive rewrite is required and normal durable grants do not require reconnect/reauthorization.
- This is the trust-bootstrap release for signed update manifests: older installed binaries may acquire this release under the historical HTTPS + SHA-256 path; once this signing-enabled binary is active, later setup/update manifests fail closed unless the publisher signature verifies.
- Rolling back to v0.3.4 hides the delete control and the collapsible animation while preserving all data.
- Existing Paths, Commands, MCP provider definitions, provider credentials, Owner Passphrase, audit/usage databases, durable OAuth grants/token families, and harness state remain preserved by the normal update path. Pending authorization transactions/codes and managed Task Runtime state remain process-local and reset on restart.

## Verification status

- Independent A01–A10 re-audit on 2026-09-25 found no new authority bypass in OAuth/policy/filesystem/exec/tasks/providers/context/Owner/Debate/audit-usage flows. Follow-up ingress review fixed missing Origin enforcement before Owner/OAuth dispatch and explicitly documented the bounded shared-peer Owner lockout trade-off instead of weakening the pre-KDF abuse cutoff.
- The public release workflow builds Linux x64 and Windows x64 natively and promotes the tag to stable only after clean public User Install acceptance succeeds for both targets plus the installed `/usage` Chromium acceptance.

## Supported / prebuilt targets

- Linux x64 standalone and User Install remain public release targets.
- Windows x64 standalone and User Install remain public release targets when the release workflow's native Windows build and clean public Windows acceptance are green.
- Linux System Install remains implemented; its broad support claim still requires the separate disposable-systemd-host evidence defined in `RELEASE.md`.
- Windows System Install/service mode is not supported.
- Source runtime remains Node.js `>=22.13.0 <25`.

## Known limitations

- Deleted debates cannot be recovered; there is no soft-delete or trash retention in V1.
- Real ChatGPT/live-tunnel OAuth acceptance and the production `release-signing` GitHub Environment configuration remain release gates; source tests do not substitute for those external/live checks.

## Rollback

- Normal rollback continues to use verified immutable release metadata and preserves managed state.
- Rolling back to v0.3.4 leaves v0.3.5 data intact; debates deleted while on v0.3.5 stay deleted.

See `CHANGELOG.md`, `RELEASE.md`, `docs/RELEASE_ACCEPTANCE.md`, `README.md`, `docs/USER_GUIDE.md`, and `docs/THREAT_MODEL.md` for the full operating and claim boundaries.

## Follow-up audit hardening — 2026-09-25

A post-closure independent Opencode review found one additional release-blocking local control-plane abuse gap and several bounded integrity/reliability issues. The current candidate now:

- rate-limits failed loopback control-plane Owner authentication before scrypt work;
- persists dynamic-client removal before live revocation state changes;
- releases runtime leases if MCP handler construction fails;
- bounds persisted Usage tool identifiers;
- re-hashes rollback target bytes before activation;
- bounds signed-manifest retrieval with one overall deadline;
- shares/ref-counts Debate wait notifications instead of allocating one callback per concurrent waiter.

The same review also rejected several false positives or contract-intent observations rather than changing stable behavior: Gateway-only Debate/provider access without coding-harness receipt, owned task cancellation during harness recovery, Basic-auth credential precedence, public secret-length input bounds, and synchronous authorization-code/Owner-limiter sequences.
