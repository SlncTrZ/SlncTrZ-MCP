# SlncTrZ-MCP v0.3.5

Date: 2026-09-22

## User-visible changes

- Adds Owner-only Debate deletion on the `/debate` page. Finished, timed-out (`paused_timeout`), stopped, or still-waiting debates show a Delete control next to Stop; deletion asks for confirmation and removes the debate with its full transcript, then returns to the conversation list.
- Active debates cannot be deleted directly: the Delete control stays hidden until the debate is stopped, so a live turn is never removed from under a participating model.
- Reworks the Owner Console Connections card around the display label: a Full/Gateway-only badge next to the name, no raw grant/client identifiers in the row, and inline rename through a pencil control (Enter applies, Escape cancels).
- Makes all five management cards collapsible with a smooth expand/collapse animation: Connections, Paths, MCP Servers, Commands, and Advanced. The animation is disabled under `prefers-reduced-motion`.

## Behavior

- Debate deletion is a hard delete of the debate row; participants and messages follow through existing cascade rules. Deleting an unknown debate returns not-found; deleting an active debate returns a conflict directing the Owner to stop it first.
- A model waiting on a deleted debate observes a clean `debate_not_found` on its next read instead of hanging.
- The Debate MCP surface stays at exactly six tools; deletion exists only on the Owner web path, so model contracts are unchanged.
- Connection rename and per-grant profile switching remain available in the Owner Console. The row-level Client Default action is intentionally removed from the normal UI; the existing Owner CLI/control-plane `client-default` compatibility primitive remains supported for setting the profile of future grants from a client and does not mutate existing grant profiles.

## Security-relevant changes

- `DELETE /owner/api/debates/:id` requires an authenticated Owner session plus CSRF, consistent with the existing stop/resume endpoints.
- Connection listings still expose no bearer/refresh token values or hashes.
- The standalone updater/setup path now requires an Ed25519 publisher signature on the exact canonical `manifest.json` bytes before parsing the manifest or activating a downloaded artifact. The release still verifies declared artifact size and SHA-256 after manifest authentication.
- Signing private material remains CI-only; the standalone runtime embeds only the public verification key.

## Migration / restart / reauthorization

- No managed-state migration in this release and no reconnect or reauthorization is required; all v0.3.4 managed state remains valid.
- This is the trust-bootstrap release for signed update manifests: older installed binaries may acquire this release under the historical HTTPS + SHA-256 path; once this signing-enabled binary is active, later setup/update manifests fail closed unless the publisher signature verifies.
- Rolling back to v0.3.4 hides the delete control and the collapsible animation while preserving all data.
- Existing Paths, Commands, MCP provider definitions, provider credentials, Owner Passphrase, audit/usage databases, and harness state remain preserved by the normal update path.

## Verification status

- Linux source/reliability gate passed on the release branch before tagging, including Owner delete across waiting/stopped debates, refusal for active debates, not-found on repeat delete, Owner API auth/CSRF/conflict mapping, and the `/debate` delete control contract.
- The public release workflow builds Linux x64 and Windows x64 natively and promotes the tag to stable only after clean public User Install acceptance succeeds for both targets plus the installed `/usage` Chromium acceptance.

## Supported / prebuilt targets

- Linux x64 standalone and User Install remain public release targets.
- Windows x64 standalone and User Install remain public release targets when the release workflow's native Windows build and clean public Windows acceptance are green.
- Linux System Install remains implemented; its broad support claim still requires the separate disposable-systemd-host evidence defined in `RELEASE.md`.
- Windows System Install/service mode is not supported.
- Source runtime remains Node.js `>=22.13.0 <25`.

## Known limitations

- Deleted debates cannot be recovered; there is no soft-delete or trash retention in V1.
- GPT web and Pi/OpenCode real-client field validation continues after release for this owner-only deployment and is not claimed as completed pre-tag evidence.

## Rollback

- Normal rollback continues to use verified immutable release metadata and preserves managed state.
- Rolling back to v0.3.4 leaves v0.3.5 data intact; debates deleted while on v0.3.5 stay deleted.
