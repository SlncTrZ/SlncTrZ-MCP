# SlncTrZ-MCP v0.4.7

Date: 2026-10-15

This release ships owner-issued Host Tokens (ADR-030) for headless and durable clients,
Client Registry Hot Reload (A4), Provider Credential Health (A5), and verified consent
completion delivery with comprehensive Linux systemd documentation.

## User-visible changes

- **Owner-issued Host Tokens (ADR-030):** Connect headless, durable or script clients
  (such as OpenCode, Pi, Codex) using a random 256-bit bearer token (`hst_...`) without
  browser OAuth, redirects or PKCE exchanges. Tokens have no arbitrary expiration date
  but are deleted after 15 days of inactivity.
- **Client Registry Hot Reload (A4):** Add or update client registrations in `oauth-clients.json`
  or static redirect URIs and apply them immediately via Owner Console (**Reload client registry**)
  or loopback CLI (`slnctrz-mcp owner clients-reload`) without restarting the gateway.
- **Provider Credential Health (A5):** Owner Console and authenticated `GET /owner/api/health`
  display whether required credentials for configured MCP providers are `not_required`,
  `configured`, or `missing`.
- **Consent Completion Delivery:** Delivers OAuth authorization codes via document meta refresh
  and restrictive CSP, resolving Chromium `form-action` restrictions when callbacks perform
  further redirects.
- **System Service Documentation:** Comprehensive guidance in README and Deployment guide for
  both Linux System service (`--mode system` via systemd) and rootless `systemd --user` mode.

## Security-relevant changes

- Host tokens are stored only as SHA-256 hashes in `<stateRoot>/secrets/host-tokens.sqlite3`.
  Plaintext tokens are returned once upon issuance and never retrievable again.
- Verification uses constant-time string hashing (`timingSafeEqual`) to prevent timing attacks.
- Host tokens are hard-coded to the `gateway-only` profile and `mcp:tools` scope; they cannot
  be elevated to Full profile or execute filesystem/command tools.
- Token revocation and 15-day idle deletion are atomic SQLite transactions emitting independent
  audit trail events (`issued`, `used`, `revoked`, `inactive_15d`) bounded up to 250,000 rows.
- Client hot reload validates the entire candidate before updating in-memory maps; client removal
  is rejected if active grants or tokens exist, requiring explicit Owner revocation first.
- Provider credential health returns metadata existence only, never exposing credential values,
  endpoints or command arguments.

## Migration / restart / reauthorization

- Restart the gateway process or service to activate v0.4.7.
- OAuth database schema remains v3: existing OAuth grants, dynamic client registrations and
  static redirect registrations remain valid without reauthorization.
- Host Token database (`secrets/host-tokens.sqlite3`) is initialized automatically.
- Pre-v0.3.6 upgrades: `audit.sqlite3` receives an additive migration for bounded authorization reason/operation fields.

## Supported / prebuilt targets

- Linux x64: User Install and systemd System Install.
- Windows x64: User Install via Git Bash. Windows System service remains unsupported.
- Node.js source contract: `>=22.13.0 <25` (tested on Node 22 and Node 24).
- Artifact integrity: Ed25519 publisher signature verification precedes artifact SHA-256 and
  size validation.

## Known limitations

- Host tokens lack IP or hardware device binding; protect client credential storage and backups.
- Provider credential health checks local reference presence, not upstream provider token validity.
- Restoring an older backup may restore deleted host token rows; reconcile active tokens after
  restoring from backup.

## Rollback

- Rolling back to v0.4.6 or v0.4.5 preserves OAuth v3 grants and dynamic client records.
- Pre-v0.4.7 binaries ignore the companion Host Token database and reject `hst_` bearer tokens.
- Re-upgrading to v0.4.7 re-enables active host tokens, checking the 15-day inactivity boundary.
