# SlncTrZ-MCP v0.3.3

Date: 2026-09-22

## User-visible changes

- Adds per-OAuth-grant Tool Surface Profiles: **Full** and **Gateway-only**. Full preserves the existing coding/file/exec/harness experience; Gateway-only exposes provider tools, Debate, `core.ping`, and self-restriction while hiding coding/file/exec/media/context/skills/task surfaces.
- Adds durable OAuth grant/token state in private SQLite storage so grants issued by v0.3.3 survive normal gateway restarts. Tokens are persisted only as hashes; plaintext access/refresh tokens are not stored.
- Adds durable two-participant Debate with six MCP tools: `debate.create`, `debate.join`, `debate.read`, `debate.send`, `debate.wait`, and `debate.stop`.
- Adds `/debate` live/history UI plus authenticated Owner APIs for reading, stopping, and resuming debates.
- Adds Owner Console connection-profile controls plus equivalent loopback control-plane and standalone CLI operations.
- Adds secret-free provider failure correlation and lifecycle/restart observability for incidents the gateway can actually identify.

## Tool Surface Profile behavior

- Surface Profile is independent from Restricted/Autonomous authority mode.
- The effective profile is resolved from the authenticated OAuth grant on every MCP exchange.
- An agent may permanently reduce its own grant from Full to Gateway-only with `connection.restrict`; it cannot self-promote.
- Owner operations may change a grant or client default in either direction.
- Two grants sharing one client identity remain independently configurable.
- Hidden Gateway-only tools fail closed even if invoked directly rather than merely disappearing from `tools/list`.
- Provider calls in Gateway-only bypass only the coding-harness receipt requirement. OAuth, policy, provider ownership, credential, and transport checks remain enforced.

## Debate behavior

- Debate state, transcript, turn ownership, idempotency records, deadlines, pause/completion state, and membership bindings are persisted in `<stateRoot>/debate.sqlite3`.
- V1 supports exactly two connection-bound participants.
- Membership requires both the authenticated connection and the opaque membership credential returned when creating/joining.
- `debate.wait` is bounded to a short MCP request; long reasoning budget is represented by persisted turn deadlines rather than one long HTTP request.
- Duplicate send, stale expected sequence, stop/send races, timeout pause, restart durability, and waiter wake-up behavior have deterministic regression coverage.
- Owner may stop or resume a paused Debate through `/debate`.

## Reliability / observability

- Provider audit events may include a secret-free incident correlation ID, finite failure class, and recovery state.
- Classified cases include stale/invalid provider sessions, startup unavailability, transport failure, known authorization/credential failure, protocol error, timeout, cancellation, recovery, and quarantine.
- Failed provider tool calls are still never replayed automatically after recovery.
- Gateway startup/shutdown lifecycle events are persisted with timestamps and known reasons such as SIGTERM/SIGINT.
- Release/control restart intent is carried through a one-shot, time-bounded, private lifecycle-intent record so the next startup can correlate a known restart without inventing causes for external SIGKILL/OS termination.

## Security-relevant changes

- OAuth grant/token persistence stores token hashes rather than plaintext bearer/refresh tokens.
- Gateway-only is enforced at both discovery and dispatch.
- Self-service profile mutation only allows reduction to Gateway-only; restoring Full requires Owner authority.
- Debate membership credentials are bound to the authenticated connection and are not replaced by caller-supplied connection identity.
- Owner connection listings expose grant/client/profile/scope metadata without bearer or refresh token values.
- Provider diagnostics add only finite metadata; tool arguments, provider response content, endpoints, environment data, and credentials remain outside the audit journal.

## Migration / restart / reauthorization

- Upgrading from v0.3.2 cannot retroactively persist grants that existed only in the old process memory, so existing clients may require one reconnect/reauthorization during the first upgrade to v0.3.3.
- Grants issued by v0.3.3 survive later normal gateway restarts.
- New managed state files are `<stateRoot>/oauth-grants.sqlite3`, `<stateRoot>/debate.sqlite3`, and the short-lived `<stateRoot>/lifecycle-intent.json` when a known restart is initiated.
- Existing Paths, Commands, MCP provider definitions, provider credentials, Owner Passphrase, audit/usage databases, and harness state remain preserved by the normal update path.
- Owner sessions, coding-context receipts, and managed tasks remain process-local and are recreated after restart.

## Verification status

- Linux source/reliability gate passed on the release branch before tagging, including restart durability for OAuth/Profile and Debate, Gateway-only fail-closed dispatch, provider no-auto-replay, and real-entry SIGTERM/SIGINT lifecycle tests.
- The public release workflow builds Linux x64 and Windows x64 natively and promotes the tag to stable only after clean public User Install acceptance succeeds for both targets plus the installed `/usage` Chromium acceptance.
- Named real-client validation for GPT web and Pi/OpenCode is intentionally continuing during normal owner use after release; this release note does not claim those clients as independently release-verified yet.

## Supported / prebuilt targets

- Linux x64 standalone and User Install remain public release targets.
- Windows x64 standalone and User Install remain public release targets when the release workflow's native Windows build and clean public Windows acceptance are green.
- Linux System Install remains implemented; its broad support claim still requires the separate disposable-systemd-host evidence defined in `RELEASE.md`.
- Windows System Install/service mode is not supported.
- Source runtime remains Node.js `>=22.13.0 <25`.

## Known limitations

- Debate V1 is limited to two participants.
- A finished/closed web-chat session is not reopened by the gateway; Debate does not claim a model-facing wake mechanism outside an active client session.
- External SIGKILL, host crash, power loss, or OS termination may not have an attributable lifecycle reason; the gateway records only causes it can actually know.
- Owner-driven provider configuration mutations still reload a provider runtime generation rather than performing generation-local mutation.
- GPT web and Pi/OpenCode field validation remains post-release operational acceptance rather than a pre-tag blocker for this owner-only deployment.

## Rollback

- Normal rollback continues to use verified immutable release metadata and preserves managed state.
- Rolling back to v0.3.2 restores the older in-memory OAuth grant model and removes v0.3.3 Tool Surface Profile/Debate behavior from the running binary. The v0.3.3 SQLite files remain on disk and are not treated as authorization input by v0.3.2.
- If a rollback is required during field validation, do not delete the v0.3.3 OAuth/Debate databases unless intentionally discarding that state.
