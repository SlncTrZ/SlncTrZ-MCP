# SlncTrZ-MCP v0.3.4

Date: 2026-09-22

## User-visible changes

- Adds Owner-managed connection display labels. New OAuth grants are named Agent 1, Agent 2, and so on; the Owner can rename any connection to a friendlier name.
- Rename is available in three places: the `/owner` Connections card (label field plus Rename button), the loopback control plane (`PUT /connections/label`), and the standalone CLI (`slnctrz-mcp owner rename <grant-id> <label>`).
- Reworks the Connections card layout around the display label: long grant/client identifiers truncate with ellipsis and the profile, client-default, and rename controls wrap instead of squeezing into a single row.
- Existing v0.3.3 grant databases migrate automatically on first start, backfilling Agent N names in grant-creation order. Tokens, profiles, and client defaults are untouched.

## Behavior

- Labels are cosmetic only. All authorization (profile enforcement, self-restriction, Debate membership, revocation) continues to bind to the backend grantId/clientId, which never changes on rename.
- Labels accept 1-64 characters; surrounding whitespace is trimmed. Renaming a grant that no longer exists returns a clean not-found error instead of failing.
- New grants pick the next free Agent N name based on existing labels, so the sequence stays readable even after older grants expire.

## Security-relevant changes

- Connection listings still expose no bearer/refresh token values or hashes; the label column adds display metadata only.
- The label APIs reuse the existing Owner session plus CSRF (web), Owner bearer (loopback), and passphrase-derived Owner authentication (CLI) with no new credential system.

## Migration / restart / reauthorization

- The grant store moves from schema v1 to v2 with one additive nullable-free column plus backfill; the Debate, audit, usage, and harness stores are unchanged.
- No reconnect or reauthorization is required: v0.3.3 grants remain valid and keep their profiles across the update.
- Rolling back to v0.3.3 ignores the label column; labels set by v0.3.4 reappear after updating again.
- Existing Paths, Commands, MCP provider definitions, provider credentials, Owner Passphrase, audit/usage databases, and harness state remain preserved by the normal update path.

## Verification status

- Linux source/reliability gate passed on the release branch before tagging, including label defaulting, rename durability across reopen, label validation bounds, and v1-to-v2 migration backfill order.
- The public release workflow builds Linux x64 and Windows x64 natively and promotes the tag to stable only after clean public User Install acceptance succeeds for both targets plus the installed `/usage` Chromium acceptance.

## Supported / prebuilt targets

- Linux x64 standalone and User Install remain public release targets.
- Windows x64 standalone and User Install remain public release targets when the release workflow's native Windows build and clean public Windows acceptance are green.
- Linux System Install remains implemented; its broad support claim still requires the separate disposable-systemd-host evidence defined in `RELEASE.md`.
- Windows System Install/service mode is not supported.
- Source runtime remains Node.js `>=22.13.0 <25`.

## Known limitations

- Labels are not required to be unique; two connections may share a name, in which case the grant identifier in the row metadata disambiguates them.
- GPT web and Pi/OpenCode real-client field validation continues after release for this owner-only deployment and is not claimed as completed pre-tag evidence.

## Rollback

- Normal rollback continues to use verified immutable release metadata and preserves managed state.
- Rolling back to v0.3.3 restores the older grant schema view; the v0.3.4 label data remains on disk and is reused after updating again.
