# SlncTrZ-MCP v0.4.6

Date: 2026-10-14

This patch fixes consent completion delivery for clients whose callback performs a further
redirect. Source preparation is not stable publication or a live gateway upgrade; check the
published GitHub release and running build identity separately.

## User-visible changes

- Consent completion is delivered as a document navigation instead of an HTTP redirect. Chromium applies the consent page's `form-action` policy to the whole redirect chain of the form submission, so a callback that re-redirects to a further application origin blocked the entire response and the client never received the authorization code. The completion document uses a meta refresh and keeps a manual continue link for environments where automatic navigation is unavailable.
- The consent page itself is unchanged: it still declares its own `form-action` policy for the submission it owns, and that policy still lists the pending client callback origin.
- Discovery, registration, token and revocation responses are unchanged.
- Deployment and troubleshooting guidance now documents the static-client service environment and the consent/authentication symptoms observed in deployment.

## Security-relevant changes

- The completion document sends `referrer-policy: no-referrer` and `cache-control: no-store`, and its continue link is `rel="noreferrer"`, so the authorization code is not exposed through a Referer or a cached document.
- The completion document keeps the same restrictive default policy (`default-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`) as the consent page.
- No change to PKCE verification, redirect-URI matching, client authentication, scope parsing, profile ceilings, owner authentication, token rotation or grant revocation.
- Owner-secret abuse budgets count failed authentication attempts, not successful Owner logins/approvals; this patch does not alter those budgets.

## Migration / restart / reauthorization

- Restart the installed gateway to run the fixed binary. A consent page issued by the previous process is not reusable afterwards because pending authorization transactions are process-local.
- No state schema change and no reauthorization: existing grants, dynamic client registrations and static redirect registrations remain valid.
- When upgrading from pre-v0.3.6 installations, `audit.sqlite3` receives an additive migration for bounded authorization reason/operation fields; that is an existing upgrade requirement, not a new v0.4.6 migration.
- Keep the installed launcher entrypoint and any operator-managed environment drop-ins. A service that owns a static OAuth client must reference `client.env` from its unit environment, because the launcher's `gateway.env` reader accepts only the documented runtime keys.

## Supported / prebuilt targets

- Linux x64; hosted public acceptance covers User Install. System Install claims require separate disposable-systemd-host evidence.
- Windows x64 User Install; Windows System Install/service remains unsupported.
- Release artifacts remain gated by Ed25519 publisher signature verification followed by artifact size and SHA-256 checks; this patch changes no signing behavior.
- Consent completion is covered by unit and conformance tests asserting that the response is not a redirect, that it carries the exact registered callback with `code`, `state` and `iss`, and that the completion document keeps the expected policy and referrer headers. Live browser acceptance in an installed gateway remains a separate release gate.

## Known limitations

- A browser that neither honors meta refresh nor lets the operator follow the continue link cannot complete consent automatically.
- Removing the policy's influence over the client callback chain does not remove the consent page's own `form-action` policy for its submission.
- Browser policy enforcement differs between engines and between embedded webviews; verification in the specific client application is required.
- Named real-client OAuth, live service/keyring and deployed build acceptance require separate evidence.

## Rollback

- Rolling back to v0.4.5 restores redirect-based delivery; clients whose callback re-redirects to a further origin can be blocked again by restrictive browser policy, so keep the fixed build for those clients.
- No state change is involved, so a rollback leaves grants, dynamic client registrations and static redirect registrations readable.
- Restore a coherent state/config backup if the operator-managed service environment was changed as well.
